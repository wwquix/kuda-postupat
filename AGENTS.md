# AGENTS.md — bseu-admission-monitor ("Куда поступать")

Этот файл — постоянный контекст проекта. Codex подхватывает его автоматически
в каждой сессии (из корня репозитория и из вложенных папок), поэтому здесь
живут только правила, которые верны ВСЕГДА, независимо от конкретной задачи.
Разовые задачи (что сделать сейчас) идут отдельным коротким промптом поверх
этого файла — не дублируй их сюда.

## О проекте

Веб-платформа для абитуриентов Беларуси: каталог вузов и специальностей,
мониторинг вступительной кампании, рекомендации, избранное/сравнение,
Telegram-уведомления. Рабочее название — "Куда поступать" (задаётся через
`APP_NAME` в `.env`, не через переименование папки/репозитория).

Сейчас проект — это переработка уже рабочего BSEU admission monitor
(парсер БГЭУ, FastAPI, React, SQLite) в более широкую платформу.
Это не новый проект и не переписывание с нуля.

## Технологический стек (не менять без явного запроса)

- Backend: Python, FastAPI, SQLAlchemy, SQLite, APScheduler, Alembic
- Frontend: React, TypeScript, Vite, Tailwind CSS, Recharts, lucide-react
- Прод: Ubuntu 24.04, 1 vCPU, ~2 GB RAM, ~30 GB диска, Nginx, systemd,
  один backend worker, frontend отдаётся статически
- Локально: Windows 11, PowerShell, Python `.venv`, Node.js/npm
- Без Redis, PostgreSQL, Elasticsearch, RabbitMQ/Kafka, микросервисов,
  постоянного Playwright — ресурсы VPS ограничены

## Незыблемые инварианты

Эти вещи обязаны продолжать работать после КАЖДОГО коммита:

- Парсер официального XML БГЭУ и мониторинг специальности
  «Экономическая информатика» (дневная платная форма, балл 276)
- Расчёт конкурса, предполагаемого проходного диапазона, примерного места
- История snapshots и защита от дублирующихся snapshots
- APScheduler, Telegram-уведомления, FastAPI API, React dashboard
- Существующие PowerShell-скрипты: `setup.ps1`, `start-dev.ps1`,
  `stop-dev.ps1`, `refresh.ps1`, `check.ps1` — сохраняются в кодировке
  UTF-8 with BOM (совместимость с Windows PowerShell 5.1)
- Старые API endpoints БГЭУ остаются доступны напрямую или через
  compatibility layer / redirect
- Существующие тесты не удаляются без замены эквивалентными

Если новая архитектура конфликтует с этим списком — сначала строится
совместимость, потом уже развивается новое, а не наоборот.

## Git

- Никогда не `push --force`
- Не пушить и не открывать PR без явного запроса пользователя
- Рабочая ветка: `feature/platform-redesign`
- Один milestone = один осмысленный коммит с понятным сообщением
- Перед началом крупного этапа — чистое рабочее дерево (`git status`)
- Не коммитить: `.env`, файлы SQLite, `.venv`, `node_modules`, логи,
  PID-файлы — проверяй `.gitignore` перед коммитом

## Секреты

- `TELEGRAM_BOT_TOKEN` и любые другие секреты никогда не появляются в:
  консольном выводе, отчётах, логах, тестовых fixtures/snapshots,
  frontend-коде, HTTP-ответах, Git-истории
- Секреты читаются только из `.env`, который не перезаписывается вслепую

## Тесты и проверка (гоняются после каждого milestone, не только в финале)

```
# backend
pytest
pytest -m live        # live-интеграционный тест БГЭУ, отдельный маркер
ruff check .

# frontend
npm run lint
npm run typecheck     # tsc --noEmit
npm run build
```

Этап не считается завершённым, пока эти команды не прогнаны и не показаны
их результаты.

## Честность данных

- Никогда не показывать выдуманные значения: `0 BYN`, `0 мест`,
  пустые проходные баллы, "общежития нет" без официального подтверждения
- Для неизвестных данных — понятный текст-заглушка
  ("Информация дополняется", "Стоимость уточняется"), а не `null`/пустая строка
- У любого факта о вузе должны быть `source_url` и дата проверки
- Список допустимых источников и порядок их приоритета — см.
  `docs/universities-source-audit.md`

## Архитектурные предпочтения backend

- Не собирать backend в один файл — разделение на
  `api/adapters/models/schemas/services/repositories`
  (детали — `docs/platform-redesign.md`)
- Новый вуз подключается через адаптер + registry
  (`adapter_registry.get(university_code)`), без цепочек `if/elif` по коду вуза
- SQLite остаётся основной БД на этом этапе

## Объём работы за одну сессию

- Один запуск/сессия Codex = один milestone из `docs/roadmap.md`,
  а не весь проект целиком
- В конце milestone — короткий summary (что сделано, что проверено,
  что дальше) и git checkpoint, прежде чем переходить к следующему
- Если задача выглядит так, будто требует переписать больше пяти модулей
  или закрыть больше одного этапа из roadmap — сначала предложи план
  и дождись подтверждения, а не делай всё сразу
